# Round 2 — Critique: Technical Feasibility & Phase Sequencing

**Scope:** Critique-only pass over `docs/planning/enhancement_plan_draft_v1.md` (the draft) against the actual codebase. No application code was changed. Method: read the three Round 1 source audits in full, then spot-checked 2–3 items per phase (A–J) directly against the referenced files, plus traced the concrete data/infra dependencies (Supabase tables, sync direction, routing, build scripts) each phase actually needs. Every claim below cites the specific file(s) read.

**Headline finding:** the draft's biggest blind spot is that it treats "port X to server cron" (Phase F) as bounded, contained work when several of the domains it targets (calendar events, CRM sequences) have **zero Supabase table today** — not just an unwired cron step. It also under-weights that billing/agreements data is already server-truth (via Stripe webhook), which actually makes Phase E *easier* than the draft implies, and it has two admin pages in its own consolidation phase that are already dead/unrouted code, not live nav clutter.

## 3. Phases to merge or split further (with file-ownership notes)

### Merge candidate: D1 + D2 + D5 (all three touch `PricingPage.tsx`'s tab logic)

### Split further: Phase I's admin-nav items are NOT one atomic unit
I1 (merge Growth/CMO pages), I2 (confirm CRM nesting — now answered, see §4), I3 (confirm dev page hidden — now answered, see §4), and I4 (check UX command page overlap) touch four **unrelated** file clusters: I1 touches `App.tsx` routes + `adminNavLanes.ts` + the growth/CMO page files themselves; I2/I3 are now no-ops (§4); I4 touches only `AdminSitewideUxCommandPage.tsx`/`AdminStudioUxCommandPage.tsx`. **These can safely run in parallel** (unlike D1/D2/D5) since they don't share files — but I2 and I3 should be re-scoped from "audit tasks" to "close out, already true" per §4, freeing that agent-time for I1/I4 instead.

## 5. Revised phase order recommendation

**Revised order: A → E1a (revenue/MRR only) → B → F1+F2 (combined infra wave) → C → G2 → D → F3 → remaining G → H → I → J**

Justification, answering the draft's own "Open questions for Round 2" directly:

1. **"Should E/F be pulled ahead of B/C?"** — Partially yes, but not uniformly. Split Phase E: **E1a (MRR/revenue-by-channel from already-server-truth Agreement data) should move to position 2**, right after the zero-risk Phase A fixes, because (a) it's Very-High-impact per all three audits, and (b) per §1/§2, it does **not** depend on any Phase F work — it's blocked only by writing one new admin-scoped aggregate query, which is genuinely cheap now that we've confirmed billing already has server truth. **E1b (CAC) and E2-E4 stay later**, gated on a new spend-input mechanism that doesn't exist yet. Full Phase F (server reliability) should still come before Phase C/D's newer public-content investment, because F is revenue-protective infrastructure (an agent-tick that silently doesn't run on a slow week is a bigger dollar loss than a missing blog post is a missed opportunity) — but F should be resequenced internally (F1+F2 combined infra wave, F3 after) per §2/§3, and F should land **before** Phase C/D commit to net-new public surface area, so the team isn't building on top of a fragile follow-up engine.
2. **"Does G2 need F2?"** — No (see §2) — G2 can and should move earlier, right after F1+F2 land (not because it's blocked, but because F2 landing measurably improves G2's data completeness, and doing G2 immediately after gives the freshest, most complete join). It does not need to wait for all of Phase F, D, or C.
3. **"Is anything double-counted or missing across the three audits?"** — One real gap found: none of the three Round 1 audits examined `billingRepo.ts`/`billingSupabaseSync.ts`/`stripe-webhook/index.ts` in depth (the delivery audit's method section doesn't list them) — this is why the draft under-credits how billing-ready Phase E1 already is. No outright double-counting found between the three audits' recommendation lists; they're genuinely non-overlapping in scope (funnel/UX vs. agent/knowledge vs. delivery/ops).
4. **"Are S/M/L ratings realistic?"** — Mostly yes; corrections are concentrated in Phase F (F1 under-rated relative to F2) and a few Phase A/D items (A5, D3) that are cheaper-sounding than their real file/domain-model footprint — see §1 for the full item-by-item list.

Concretely, Phase C and Phase D public-facing work is **not** devalued by this reordering — it remains high-ROI, low-risk (no new infra, well-trodden pattern per §2) — it's simply sequenced after the revenue-visibility and follow-up-reliability fixes so the business can *see* whether the new public content phases are working (via E1a) and *trust* that new leads generated by C/D funnels actually get followed up on nights/weekends (via F1+F2), rather than adding more top-of-funnel volume into a follow-up engine that still silently stops running when no admin is logged in.

## 6. Anything else technically risky in the draft

- **`isOverFrequencyCap`/quiet-hours fixes (A4/A5) and Phase F's server port need to agree on one canonical suppression check.** Once CRM sequences run server-side (F2), the *server-side* send path needs its own quiet-hours/frequency-cap check — `supabase/functions/_shared/commsSuppressionCheck.ts` exists already (good, confirmed in the file listing) but Round 3 should explicitly verify it enforces the same rules A4/A5 are adding client-side, or the client fix will "fix" a code path that's about to be superseded by a server path with different (or missing) guards.
- **The draft never asks whether the *existing* `automation_rules`/`automation-runner` "notify_admin"/"nurture_enqueue" server actions overlap with what F2's ported CRM sequences would do.** `executeAutomationAction.ts` and `processDueNurtureEnrollments.ts` already run a server-side nurture/automation system in parallel with the client-side CRM sequence engine. Porting CRM sequences to the server (F2) risks **two independent server-side "should I email this person today" systems** running side by side (nurture enrollments vs. CRM sequence enrollments) unless F2's design explicitly reconciles with the existing nurture/automation-rule tables rather than bolting on a third parallel send-decision system. This is worth a design pass *before* F2 implementation starts, not just an execution detail.
- **`AdminBillingPage.tsx` was not re-read in this pass** (out of scope for the phases spot-checked) but given the E1 finding that `Agreement` already has real fields for aggregate revenue math, it's worth a fast follow-up check of whether `AdminBillingPage.tsx` already has any partial rollup logic that E1 could reuse rather than rebuilding from scratch — flagging as a likely quick win for whoever picks up E1a, not confirmed either way in this pass.
- **Orphaned admin page files (§4) suggest a broader pattern** — worth a one-time repo-wide check (not scoped to any single phase) for other `src/pages/admin/*.tsx` files that are never imported in `App.tsx`, since at least 3 were found here (`AdminSovereignGrowthCommandPage`, `AdminCmoAutopilotPage`, `AdminLeadEngineSystemDevPage`) without an exhaustive search. This is a cheap, mechanical audit (`grep` every admin page filename against `App.tsx`'s import list) that could surface more dead code the draft's phases don't currently account for cleaning up.
