## 1. Contradictions found between the 3 source audits

### 1.1 Direct factual contradiction: does the non-citizen/international credit doctrine have a UI surface or not?

- **Pages/UX audit** (`round1_pages_ux_funnel_audit.md`, Method section + §2) states plainly: *"the non-citizen/international credit rules live at `/business/profile` (`src/pages/business/BusinessProfilePage.tsx:41-108`, also `ProtectedRoute`, confirmed at `src/App.tsx:1953-1975`)."* It even lists this as one of three doctrine surfaces that exist but are gated.
- **Agent/Content audit** (`round1_agents_content_knowledge_audit.md`, "Knowledge base / RAG quality gaps") states the opposite: *"International/non-citizen credit doctrine has zero dedicated UI surface... no page, panel, or component renders this content directly."* This claim is repeated again in that audit's "Unique differentiators not yet surfaced" section and its prioritized recommendation #7.
- **Verified against the actual code in this pass:** `BusinessProfilePage.tsx` (lines 41–46, 57–108) directly imports `getFundingRulesForApplicantType` and `getInternationalCreditSystem` from `internationalAndNonCitizenCreditRepo.ts`, maintains `selectedApplicantType`/`selectedCountryCode` state, and renders `matchedFundingRules`/`matchedCountrySystem` — this **is** a dedicated (if gated) UI panel for exactly this content. The Pages/UX audit is correct; the Agent/Content audit is wrong on this specific point.
- **Consequence for the draft plan:** Phase B3 of `enhancement_plan_draft_v1.md` inherited the *incorrect* claim verbatim — *"Give the non-citizen/international credit doctrine a public-facing page or portal panel pointed at from `/business/funding` (currently zero dedicated UI surface)."* The "currently zero dedicated UI surface" framing is false and should be corrected to: *a portal panel already exists at `/business/profile`; the real gap is that it's gated and has no public/SEO equivalent, and `/business/funding` doesn't link to it.* This changes the effort estimate (reuse-and-link vs. build-from-scratch) and should be flagged before Round 3 finalizes scope.

### 1.2 Framing tension: "~97% live" agent capability vs. "doesn't run without an open browser tab"

- The **Agent/Content audit** concludes the growth-agent capability layer is *"~97% live"* based on a grep of `tier: 'preview'`/`tier: 'soon'`/TODO markers in `growthAgentRegistry.ts` — i.e., it measures **code completeness** (is the reasoning call real vs. stubbed).
- The **Delivery/Efficiency audit** concludes the same system is *"not production-grade for a real 24/7 business"* because `runGrowthAutopilotTick()` and `runDueCrmSequenceSteps()` only execute when an admin has a mounted React page open — i.e., it measures **runtime availability**.
- These are not technically contradictory (different axes), but read together without care they *sound* contradictory ("97% live" vs. "doesn't run at all some days"), and a reader skimming only the Agent audit's headline stat could wrongly conclude the system is operationally sound. The draft plan's cross-cutting theme paragraph does correctly synthesize both axes ("genuinely built... but not running when no admin has a browser tab open"), so this was **handled correctly at the top of the draft**, but the two source stats are never reconciled inside the phase items themselves (Phase F). Round 3 should explicitly state in Phase F's rationale that "live" (agent audit) and "runs unattended" (delivery audit) are different claims, so a future reader of just the draft plan doesn't inherit the same ambiguity.

### 1.3 Minor overlap-as-near-contradiction: Hannah's "(AI)" mislabel is reported as if a single-file fix, but two audits each hold half the picture

- The Agent/Content audit frames this purely as a registry/label problem (`growthAgentRegistry.ts` line 199).
- The Delivery/Efficiency audit never mentions Hannah's label at all, but its own finding — that most growth-agent ticks require an open admin tab — means that *even if* `hannahSyndicationWatcher.ts` were wired to `runAgentBrainStep()` per the Agent audit's fix, the capability still wouldn't run unattended per the Delivery audit's finding. The draft plan's Phase A1 (fix the label) and Phase F2 (port the tick engine server-side) are in different phases with no cross-reference. This isn't a contradiction so much as an **un-flagged dependency** — Round 3 should add a note to A1 that the fix is cosmetic/correctness-only until F2 lands, so nobody reports A1 "done" and assumes Hannah's channel-watcher now runs 24/7.

### 1.4 No contradictions found on the core cross-cutting thesis

All three audits independently converge on the same root cause (deep, real capability that's either gated, client-side-only, or untold in marketing copy) using non-overlapping evidence — this triangulation is a genuine strength of the Round 1 research and the draft plan's synthesis of it is accurate. Aside from §1.1–1.3 above, no other material contradictions were found between the three source documents.

## 4. Missing "Phase K" opportunities (net-new items not in the draft at all)

These are gaps a genuinely thorough reading of the prior sprint's actual code (not just the three Round 1 audits) surfaces, and that don't appear anywhere in `enhancement_plan_draft_v1.md`:

### 4.1 Media-technique library is a static reference deck, never actually consulted by the copilot it was built for

`contentStudioMediaEngineRepo.ts`'s own header comment states its intended consumer is *"the Content Studio copilot brain (see `videoCreationCopilotBrain.ts` and `mediaCommandBrain.ts`) so it can eventually recognize production gaps... and suggest a concrete next technique instead of a generic prompt."* A grep of both `videoCreationCopilotBrain.ts` and `mediaCommandBrain.ts` for any reference to the technique repo, or even the word "technique," returns **zero matches**. The only consumer of this ~150-entry library today is `MediaTechniqueLibraryPanel.tsx`, a manually-browsable chip picker inside `/admin/content-studio` — a human has to remember to open it and read it themselves. The "copilot recognizes a gap and suggests a technique" behavior the file was explicitly built to enable **does not exist yet**, and none of the three Round 1 audits caught this because none of them opened `contentStudioMediaEngineRepo.ts` directly or traced its "intended consumer" comment against the actual copilot-brain files. **Recommend: Phase K1** — wire a lightweight gap-check into `videoCreationCopilotBrain.ts`/`mediaCommandBrain.ts` that checks a draft's declared platform/format against `getVideoTechniquesByCategory`/`getImageTechniquesByCategory`/etc. and surfaces one concrete missing technique (e.g., "no caption-burn-in plan yet") instead of the library sitting as pure reference. This is the single most direct answer to task 3's question about the media engine reaching genuine day-to-day usefulness — right now it's a library nobody is required to open.

### 4.2 Media-technique knowledge chunks are missing the internal-only tag their sibling psychology-architecture chunks correctly received

This is a concrete, previously-uncaught technical finding, not a style opinion. In `src/lib/finelyKnowledgeIndex.ts`:

- The psychology-architecture chunk builder (`buildFinelyKnowledgeChunks`, psychology section) explicitly tags every profile chunk `'internal_only'` (line ~418) with a comment: *"internal agent-reasoning grounding, NOT partner-facing... excludes it from public/partner-facing search the same way billing/CRM ops content is excluded."*
- The **content-media-engine chunk builder** (`buildContentMediaEngineChunks`, ~lines 423–484), built in the same sprint phase and serving the same "internal staff tool" purpose, tags its chunks only with content-descriptive tags (`'video_production'`, `'content_studio'`, `'media_production'`, category names) — **none of which appear in `INTERNAL_REFERENCE_TAGS`** (`{'billing','crm','pipeline','dunning','agreements','entitlements','internal_only'}`, line ~662). Each chunk also carries `route: '/admin/content-studio'`.
- Because `isPublicSafeKnowledgeChunk()` (line 668) only excludes `'reference'`-source chunks by tag (not by route), and these chunks' tags don't match any excluded tag, **these staff-only production-technique chunks pass `isPublicSafeKnowledgeChunk()` and are eligible for public/partner chat retrieval** via `searchFinelyKnowledgePublic`. `sanitizeFinelyPublicReply()` only strips literal `/admin`/`/portal` route substrings and a short list of ops-jargon terms from the final reply text — it does not prevent retrieval of the underlying chunk, and the chunk text itself (technique descriptions, "tools that do this well" lists, platform-fit notes) contains none of the filtered jargon, so it would pass through unmodified if retrieved.
- **Practical impact:** low-severity (this is internal production-technique reference content, not sensitive data), but it's a genuine boundary inconsistency in the exact subsystem the Agent/Content audit praised for its "careful, deliberate" public/internal separation. **Recommend: Phase K2** — add `'internal_only'` (or a new `'content_studio_internal'` tag) to the four media-engine chunk builders in `finelyKnowledgeIndex.ts`, mirroring the psychology-profile pattern exactly. This is an `S`-effort, zero-ambiguity fix that none of the three Round 1 audits found because none of them diffed the tagging logic between the two sibling "internal knowledge" repos added in the same sprint.

### 4.3 Psychology architecture only profiles the *sender's* communication style, never the *recipient's*

All three Round 1 audits (correctly) evaluate whether the psychology-architecture layer is wired into agent/Ruth prompts. None of them ask the adjacent question: does the system ever infer or store anything about a *partner's* communication style/preferences (their own OCEAN/DISC-adjacent signal — e.g., "responds better to short direct messages," "gets anxious with dense legal text") so that Alex/Ruth/a human Credit Specialist can adapt tone *to that specific partner*, not just apply one fixed sender-side persona to everyone? Nothing in `agentPsychologyArchitectureRepo.ts`, `crmRecordsRepo.ts`, or `crmProspectsRepo.ts` (skimmed for this pass) stores a per-partner communication-style field. This is a genuinely differentiated feature space "top-tier human account managers" naturally do (reading the client, not just performing a fixed persona) that the current architecture doesn't attempt in either direction. **Recommend: Phase K3 (longer-horizon, pairs with G2/G4)** — once agent-action→outcome attribution (G2) exists, consider deriving a lightweight per-partner communication-preference signal (e.g., "responds faster to direct/short messages" vs. "engages more after a reassurance-first message") from actual reply/engagement patterns, and feed it back into Alex's/Ruth's prompt construction the same way the agent's own persona profile is fed in today.

### 4.4 No agent uses the doctrine repos (debt-litigation, business-credit tier, non-citizen funding) as *live reasoning grounding* for their own outreach — only for chat RAG retrieval and gated portal panels

All three doctrine repos are consumed by `finelyKnowledgeIndex.ts` (RAG) and by their respective gated portal pages, but a review of `calebReasoningSubagents.ts`, `estherStrategySubagent.ts`, and `benjaminPartnershipSubagent.ts` (per the Agent audit's own method list) shows none of them import these doctrine repos directly to ground a growth-agent decision (e.g., Caleb qualifying a lead who mentions "I got served papers" doesn't get to reason using `debtLitigationDoctrineRepo.ts`'s `debtType`/`phase` taxonomy; Esther planning a weekly content focus doesn't pull `businessCreditDoctrineRepo.ts`'s tier-progression data to pick which case-study angle to push). This is a distinct gap from "the content isn't public" (Pages/UX audit) or "the content isn't in FAQ" — it's "the content isn't even informing the growth team's own decisions," and none of the three audits raised it. **Recommend: Phase K4 (pairs naturally with C1)** — once C1's public articles exist, have Caleb's Qualifier and Esther's weekly-focus reasoning explicitly reference the relevant doctrine repo's structured fields (debt type/phase, business tier, applicant type) as part of their `runAgentBrainStep()` context, not just plain-English team-context text.

## 5. Compliance/legal review gap

**This is a real, missing safeguard in the draft plan.** Finely Cred operates in three regulated domains simultaneously — consumer credit disputes (FCRA, CROA, Regulation V), debt collection defense (FDCPA, state civil-procedure/court-deadline rules), and business funding (ECOA, state lending disclosure rules) — and the draft plan's flagship content initiative, **Phase C1** ("Publish 8–12 public, SEO-indexable articles from the debt-litigation, business-credit-tier, and non-citizen doctrine repos"), has **no compliance-review or legal-review step anywhere in its item description, its effort estimate, or its "Open questions for Round 2" list.**

Why this matters concretely, not just in the abstract:

- `debtLitigationDoctrineRepo.ts`'s own header disclaimer explicitly warns that its content covers *"answer deadlines, statutes of limitation, garnishment exemptions, service-of-process rules, foreclosure procedure, tax collection procedure"* which *"varies significantly from state to state, changes over time, and can turn on facts not captured here"* and that the file *"must never substitute for advice from a licensed attorney... especially anywhere close to a court deadline."* That disclaimer was written assuming this content stays inside a gated portal panel (`PartnerDebtPage.tsx`) reviewed in context by a human Credit Specialist working an active case. Republishing the same underlying facts as static, indexed, evergreen public articles (Phase C1) changes the risk profile: a public article can't attach the same "your specific case may differ, ask your specialist" framing a live portal interaction naturally has, and once indexed by Google it will be read by people Finely Cred has no relationship with and no ability to correct in real time if a cited statute changes.
- The existing codebase already has a precedent for a **pre-publish compliance/disclosure review gate** for a different content type — `SocialDisclosureReviewPanel.tsx` / `socialDisclosureLayer.ts` gate social-content claims before they go out. **No equivalent review step is proposed anywhere in Phase C** for the new public doctrine articles, despite the underlying content (state-specific legal procedure, statutory citations, lending program terms) carrying materially higher regulatory exposure than a social post.
- Phase C4 (stretch: state-specific debt-defense landing pages) compounds this — state-by-state legal content is exactly the category the repo's own disclaimer flags as "varies significantly by state" and is the single highest-risk item in the entire draft plan from a compliance standpoint, yet it carries no more scrutiny in the draft than a lower-risk item like the FAQ additions (B5).
- None of the three Round 1 audits raised this either — the Pages/UX audit recommends C1's underlying idea (publish 8-12 articles) as its #1 prioritized recommendation without a compliance caveat; the Agent/Content audit doesn't touch public content compliance at all; the Delivery/Efficiency audit's compliance section is scoped narrowly to email/mail deliverability (suppression, bounce handling, quiet hours) and never touches content-accuracy/legal-review compliance.

**Recommended fix for Round 3:** Add an explicit **Phase C0 (or a C1 sub-step)** — "Legal/compliance review pass on each doctrine-derived public article before publish, plus a recurring re-verification cadence (e.g., semiannual) given the source repos' own disclaimers note that statutes and state rules change over time." This should sit *before* C1 in sequence, not after, and should explicitly flag C4 (state-specific pages) as needing the highest scrutiny given it's the most state-law-dependent content in the whole plan.

## 6. Partner (post-sale) experience gap

The user's premise that "most of the draft is prospect/marketing-facing" is **partially true but should be qualified** — a direct read of `PartnerDashboardPage.tsx` and the wider `src/pages/portal/` directory (42 files) shows the partner portal is already far more built-out than either the Pages/UX audit or the Delivery/Efficiency audit gives it credit for: it already has a `JourneyRoadmap`, `PartnerOnboardingProgress`, `PartnerActivityTimeline`, `PartnerCreditRestoreCommandStrip`, `PartnerSuccessExperiencePanel`, `PartnerSocialProofStrip`, `PartnerCreditLanesPanel`, `RoleWorkflowPanel`/`computeRoleWorkflowProgress`, and a `PartnerHubLauncherGrid` fanning out to 40+ dedicated partner pages (disputes, debt, wealth paths, letters vault, bankruptcy, identity theft, tradeline marketplace, courses, billing, calendar, messages, projects, tasks, etc.). **Partner-facing progress transparency is not a gap** — it is one of the most mature parts of the codebase, and neither the Pages/UX audit nor the Delivery/Efficiency audit mentions this depth at all (both focus on the public/pre-sale side and the admin/ops side respectively, leaving the partner portal itself almost entirely unexamined by any of the three Round 1 audits — see §7.4).

That said, two real partner-experience gaps were found that the draft plan does not address, because none of the three source audits looked at the partner portal directly:

- **6.1 — No partner-facing referral mechanic exists inside the partner portal**, despite a fully-built backend referral system existing elsewhere in the codebase (`src/lib/referralGrowthEngine.ts`, `src/data/referralGrowthRepo.ts`, `src/lib/referralRewardsEngine.ts`, `src/features/admin/AdminReferralGrowthPanel.tsx`, `src/features/crm/referrals/CrmReferralDashboard.tsx`). A repo-wide grep for "referral" inside `src/pages/portal/` returns **zero matches** — the referral-code click/conversion tracking, rewards engine, and admin dashboard all exist, but there is no "share your referral link / see your reward status" panel anywhere a logged-in partner can see. This is a distinct, concrete, and currently-unaddressed gap: the infrastructure for partner-driven referral growth is real and built, but it's entirely invisible to the partner who would actually generate the referral. **This did not appear in any of the three Round 1 audits and is entirely absent from the draft plan.**
- **6.2 — No visible post-sale retention/upsell path inside the partner journey UI.** `PartnerDashboardPage.tsx` surfaces `PartnerCreditRestoreCommandStrip`, `PartnerFundingCommandStrip`, and `DenefitsEnrollmentPanel` (financing-related), but a targeted look for an equivalent "you've completed X, here's a natural next program" cross-sell surface (e.g., a personal-credit-restore graduate being offered Wealth Builder or Business Credit once their score stabilizes) was not found wired into the dashboard's default view — cross-sell/upsell logic appears to exist only as one-off components (`PartnerFundingCommandStrip`) rather than a lifecycle-stage-aware recommendation. This is a lighter-weight gap than 6.1 (some of the building blocks — case studies, pricing tiers — already exist and could be assembled), but it's still unaddressed by any Round 1 audit or the draft plan.

**Recommended fix for Round 3:** Add a **Phase K5 — "Partner referral surface"** item (S/M effort: build a partner-facing panel reusing the already-built `referralGrowthEngine.ts`/`referralRewardsEngine.ts` backend, likely on `PartnerDashboardPage.tsx` or a new `/portal/referrals` route) and flag 6.2 as a lower-priority follow-on once 6.1 ships, since 6.1 has a fully-built backend today and 6.2 does not.
